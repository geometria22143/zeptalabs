# Implementation Plan: Fix Data Synchronization Issue — Admin Posts Not Visible to Viewers

## Problem Analysis

**Current Architecture (CONFIRMED by code inspection):**
- The application has a proper Express backend server (`server.ts`) with REST API endpoints
- Server stores posts in `data/posts.json` (currently empty `[]`)
- Client-side code in `postStorage.ts` already has full API integration implemented:
  - `fetchAllPosts()` calls `/api/posts` to fetch from server
  - `createPost()` calls `POST /api/posts` to create on server
  - All interactions (likes, shares, comments) call server endpoints
- The server has proper CRUD endpoints for posts at `/api/posts`

**Root Cause Identified:**
The synchronization logic IS already implemented correctly. The issue is that `data/posts.json` is empty on the server, which means:
1. Either the admin's posts were only saved to their browser's localStorage (offline mode fallback) and never synced to server
2. Or the server file `data/posts.json` was reset/cleared
3. The dist folder may have stale static files that don't include the latest server-side data

**The Real Fix:**
Since the architecture is already correct (client fetches from server, server stores in posts.json), the problem is likely:
1. The built dist files need to be regenerated to ensure they connect to the backend properly
2. Any posts stuck in admin's localStorage need to be synced to the server via the existing `/api/posts/sync` endpoint
3. The polling interval (3.5 seconds) in App.tsx should work, but we need to ensure it's running in production

## Key Design Decisions

**Decision 1: Keep existing architecture, fix the execution**
- Rationale: The client-server architecture is already correctly implemented with proper API endpoints and fetch logic. The issue is operational (empty data file, stale build, or localStorage not syncing), not architectural. Rebuilding or refactoring would be unnecessary and risky.

**Decision 2: Add diagnostic logging before making changes**
- Rationale: We need to confirm where posts are actually going (localStorage only vs server). Logging in server.ts will show us if posts reach the backend or are stuck client-side.

**Decision 3: Rebuild dist folder as a mandatory step**
- Rationale: The dist folder may contain old bundled code that doesn't include the server API calls. A fresh build ensures the deployed code matches the source.

**Decision 4: Implement manual sync button as a safeguard**
- Rationale: The automatic sync logic in `fetchAllPosts()` already handles unsynced posts, but a manual button gives admins explicit control and visibility into the sync process, useful for troubleshooting.

**Decision 5: Prioritize server as source of truth over localStorage**
- Rationale: localStorage should be a cache and offline fallback only. The server's `data/posts.json` must be the authoritative source. Viewers should never read from their own localStorage for posts created by others.

1. Admin creates a post → it is immediately saved to `data/posts.json` on the server

3. All users see the same posts because they all read from the shared server-side `data/posts.json`
4. localStorage is only used as a temporary cache to improve performance, not as the source of truth
