# Netlify Blobs persistence bug fixes

Fixes critical bugs where mutations to posts, users, and logo were not being persisted. The previous commit implemented Netlify Blobs storage infrastructure with read/write helpers but forgot to actually call `writePosts()`, `writeUsers()`, and `writeLogo()` in several mutation endpoints. This meant likes, shares, comments, deletes, batch syncs, user creation, and logo changes were lost after every function invocation.

**Watch for:** None — this is a straightforward bug fix completing the persistence implementation started in the previous commit.

**Verdict**: APPROVED

## High-level view

The posts function was missing `writePosts()` calls in 7 mutation endpoints: batch sync, like toggle, share increment, comment creation, comment like, post deletion, and comment deletion. The users function was missing `writeUsers()` call in the user creation endpoint and `readUsers()` calls in all read operations. The logo function was storing state in a module-level variable instead of blob storage. All three functions now correctly implement the read-modify-write pattern for every operation.

## Posts function: Missing write operations

Seven endpoints in `posts.ts` were reading from blob storage, modifying data in memory, but never writing the updated data back. The `writePosts()` helper existed but wasn't being called.

**POST /api/posts/sync**: Batch sync endpoint accepted incoming posts from client cache, filtered duplicates, added new posts to the in-memory array, then returned without persisting. Every batch sync silently lost data.

**POST /api/posts/:id/like**: Like toggle modified the `likedBy` array and updated the `likes` count in memory, returned the new state to the client, but never wrote to storage. Users saw likes increment in their own browser but the change vanished on the next read from a different function instance or after a cold start.

**POST /api/posts/:id/share**: Share counter incremented in memory, returned to client, never persisted.

**POST /api/posts/:id/comments**: New comments were pushed to the post's `comments` array in memory, assigned IDs, returned to the client, never persisted. Comments appeared briefly then vanished.

**POST /api/posts/:postId/comments/:commentId/like**: Comment like toggle had the same issue as post likes — modified in memory, returned, lost on next read.

**DELETE /api/posts/:id**: Post deletion filtered the posts array in memory but never wrote the result. The post reappeared on the next GET request.

**DELETE /api/posts/:postId/comments/:commentId**: Comment deletion filtered comments in memory, never persisted.

The fix adds `await writePosts(posts);` immediately after the in-memory modification in each endpoint, before returning the response. All seven endpoints now follow the correct read-modify-write pattern: `readPosts()` → modify → `writePosts()` → return response.

## Users function: Module-level variable instead of blob storage

The users function was still using `let users: ServerUserItem[] = []` at module scope. This is the in-memory pattern that the Netlify Blobs migration was meant to replace.

**POST /api/users**: Accepted new user registration, pushed to the module-level array, returned success. The user record was lost on the next function invocation.

**GET /api/users** and **POST /api/users/find**: Both read from the stale module-level array instead of fetching fresh data from blob storage.

The fix removes `let users: ServerUserItem[] = []`, adds `readUsers()` and `writeUsers()` blob storage helpers (identical pattern to `posts.ts`), and updates all three endpoints:
- GET /api/users now calls `await readUsers()` 
- POST /api/users calls `await readUsers()`, modifies, `await writeUsers()`, logs success
- POST /api/users/find calls `await readUsers()` before searching

## Logo function: Module-level variable instead of blob storage

The logo function used `let storedLogo = 'logo.png'` at module scope. Admin uploads changed this variable in memory, viewers reading from a different function instance saw the default logo.

**POST /api/logo**: Updated `storedLogo` variable, returned success, change was lost.

**GET /api/logo**: Returned the module-level variable, which might be stale or reset to default.

The fix removes `let storedLogo`, adds `readLogo()` and `writeLogo()` blob storage helpers, and updates both endpoints. GET now calls `await readLogo()` from storage. POST calls `await writeLogo(logoUrl)` to persist. The response was also changed from `{ logoUrl: storedLogo }` to `{ logoUrl }` to return the submitted value, not a stale variable.
